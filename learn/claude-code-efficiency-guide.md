## 常见误区

很多人使用 Claude Code 会踩类似的坑：
- 上下文快满了还在疯狂输出 → Claude 越用越"笨"
- 装了插件却不知道有没有用 → Token 用在刀背上

## 一、上下文管理

### 1.1 上下文腐烂阈值

Claude 官方文章指出：**上下文窗口占 30%-40% 时，就会出现上下文腐烂**。

| 窗口占用 | 建议 |
|----------|------|
| 30%-40% | 开始关注，准备管理 |
| 50%+ | 必须进行 compact |
| 60%+ | 之前习惯，现在建议提前 |

### 1.2 三大命令

#### compact（整理桌面）

**作用：** 压缩前面的对话成摘要，清掉冗余信息，保留关键内容。

**使用时机：**
| 场景 | 建议 |
|------|------|
| 同一任务超过 20-30 轮对话 | 执行 compact |
| 上下文窗口占用 50%+ | 执行 compact |
| 大模型开始回答奇怪答案 | 第一反应：compact |

```
compact 执行后：
  ✓ 文本变干净
  ✓ 后续表现回归正常
```

#### clear（清空桌面重来）

**作用：** 直接清空当前对话，重新开始。

**适用场景：**
- 任务已经完全跑偏
- 想换一个新任务

**对比：**
| 命令 | 形象比喻 | 适用场景 |
|------|----------|----------|
| compact | 整理桌面 | 当前任务有值得保留的上下文 |
| clear | 清空桌面重来 | 任务跑偏或换新任务 |

#### bytheway（不侵入上下文）

**作用：** 临时讨论，不记录到上下文窗口。

**适用场景：**
- 正在 vibecoding，突然想到产品逻辑问题 → 用 btw 讨论
- 记录一个需求到文档，等当前任务结束后再处理

```
当前 coding 任务
      ↓
btw 讨论其他问题（不侵入上下文）
      ↓
btw 把需求记录到文档
      ↓
当前任务结束
      ↓
调用文档中的需求继续工作
```

### 1.3 其他使用习惯

| 习惯 | 说明 |
|------|------|
| **引用文件指定路径** | 不要让大模型自己扫描仓库，找不到甚至会写脚本找，Token 消耗得不偿失 |
| **复杂任务用 Plan Mode** | 大幅减少 Token 消耗 |
| **给完整工作流** | 不要一步一步指导，给一个完整任务让 Claude 从头到尾执行，避免上下文过长导致幻觉和丢失 |

## 二、Pro 缓存机制

### 2.1 缓存原理

如果两次请求的前缀内容相同，Claude 直接用缓存：
- ✅ 速度更快
- ✅ Token 消耗大幅降低

**可缓存内容：**
- CLAUDE.md 的内容
- 项目文件内容
- 同一会话内的历史对话

### 2.2 缓存失效场景

| 失效原因 | 说明 |
|----------|------|
| **修改 CLAUDE.md** | CLAUDE.md 被视为整体模块，位于缓存前缀中间位置。改一个标点符号 → 从该模块开始到后续所有内容缓存全部失效 |
| **对话间隔超 5 分钟** | Claude 缓存默认 5 分钟超时，超过无新请求 → 缓存失效 |

### 2.3 缓存优化建议

| 建议 | 说明 |
|------|------|
| **有意识组织 CLAUDE.md 结构** | 减少修改频率，保持缓存有效 |
| **保持对话节奏** | 长时间等待不如保持对话 |
| **离开前先 compact** | 压缩后再离开，回来时更干净 |

## 三、常用 Skills

Skills 是可安装的能力包，把提示词和逻辑打包成命令直接调用。

### 3.1 Planning with File（使用频率最高）

**作用：** 把任务拆解成结构化计划，写入文件，review 确认后按计划执行。

**适用场景：** 所有偏复杂的任务

**工作流变化：**

```
传统开发流程：
  花一天想架构 → 几天开发

现在的工作流：
  几天和 Claude 聊设计 → 记录想法到文件 → 基于 plan file 执行 coding
  结果：代码结构、约束、规范都非常工整
```

**使用方式：**
```
/planning-with-file
  ↓
上传规划文档或让它生成计划文件
  ↓
review 确认
  ↓
按文件里的计划一步步执行
```

### 3.2 Frontend Design + UIUX Pro + Remotion

**用途：** 前端界面设计

**适合人群：** 开发人员（对 UI 设计不太擅长）

**配合使用：**
- 官网提供的素材和模板
- React 等设计软件
- 这些 Skills →事半功倍

### 3.3 NotebookLM Skill

**背景：** Gemini 降智后，NotebookLM 生成的结果不太能满足需求

**用法：** 把 NotebookLM 生成的结果给 Claude Code，让它执行后续任务

### 3.4 Everything Claude Code

**作用：** Claude Code 所有功能用法汇总，相当于内置使用手册

**优点：** 比翻官方文档快很多

**注意：**
- ⚠️ 较消耗 Token
- ⚠️ 关闭一些 MCP 后仍消耗较大
- ⚠️ 复杂任务才用得上，普通任务用不着

### 3.5 Superpowers

**特点：** 包含完整软件工程生命周期的 Skill 全集

**适合人群：** 小白刚入手 vibecoding，这一个 Skill 就够

**核心价值：** 脑爆技能

### 3.6 Claude Code（Karpathy）

**特点：** 像一个靠谱的资深工程师

**原则：**
- 先清楚再动手，不乱猜
- 能简单就不搞复杂
- 改动以最小成本进行
- 每一步尽可能验证

**适合场景：**修 bug、改老项目、重构

## 四、Hooks

Hooks（钩子）允许自定义触发器，在 Claude Code 完成某事时自动执行脚本。

### 4.1 常用场景

| 场景 | 说明 |
|------|------|
| **代码修改后自动格式化** | 每次 Claude Code 改代码 → 自动跑 `PreToolUse` 和 `lint --fix` → 不用提醒，不用担心格式乱 |
| **任务结束发通知** | 长任务完成 → 系统通知到手机。比轮询监控省 Token（原来 Claude 用轮询监控 Claude Code，现在用 Hook 回调通知） |
| **工具调用前后记日志** | 每次工具调用前后记录 → 任务结束看完整执行过程 |

### 4.2 Hook vs 轮询对比

```
传统方式（高 Token 消耗）：
Claude 触发 Claude Code → Claude 轮询监控 → 完成

Hook 方式（低 Token 消耗）：
Claude 触发 Claude Code → Hook 回调通知 Claude → 完成
```

## 五、插件推荐

### 5.1 ClaudeHUD

**作用：** 实时监控使用量和 session 上下文情况

**配合：**上下文管理技巧组合使用，效果很好

### 5.2 Claude Code（Figma 插件）

**作用：** 直接把 Figma 设计稿导入

**适合：** 配合 Frontend Design Skill

**场景：** 产品用 Figma → 设计稿直接导入 → 从设计到实现省很多

### 5.3 SentryDev

**作用：** 排查线上 bug

**流程：**
```
线上报错 → Claude Code 结合异常信息、站点、上下文 → 快速定位问题
```

**优点：** 省掉自己翻半天日志的时间
